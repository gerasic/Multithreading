# Функциональные требования

## 1. Общие требования

1.1. Система состоит из **сервера** и **клиента**.  
1.3. Обмен сообщениями: **JSON Lines** (каждое сообщение — JSON в одной строке, заканчивается `\n`).  
1.4. Сервер обслуживает **несколько клиентов одновременно**.

---

## 2. Игровые сущности

### 2.1. Items (тип продукции)

2.1.1. На сервере задан фиксированный справочник продукции:

- `Gear`
- `Plate`
- `Circuit`

2.1.1.a. `Item` в рамках проекта означает тип продукции, которую игрок запускает в производство через создание заказа.

2.1.1.b. `Gear`, `Plate`, `Circuit` не покупаются как отдельные товары в магазине. Это производственные позиции, для которых сервер считает время изготовления и награду.

2.1.1.c. Пример:

- если игрок отправляет `create_order` с `item = "Gear"`, это означает заказ на производство 1 единицы `Gear`
- после завершения такого заказа игрок получает награду в монетах, а не сам предмет в инвентарь

2.1.2. Для каждого item заданы:

- `baseTimeMs` — базовое время производства 1 единицы (мс)
- `rewardCoins` — награда за 1 единицу (монеты)

### 2.2. Player

2.2.1. Player имеет поля:

- `playerId` (целое, уникальное)
- `login` (строка, уникальная)
- `coins` (целое, >= 0)
- `machines` (целое, >= 1)

2.2.2. На сервере для игрока хранится учётная запись:

- `login`
- `passwordHash`

2.2.3. При регистрации создаётся новый player:

- стартовые монеты: `START_COINS`
- стартовые станки: `START_MACHINES = 1`

### 2.3. Order

2.3.1. Order имеет поля:

- `orderId` (целое, уникальное)
- `playerId` (владелец)
- `item` (`Gear|Plate|Circuit`)
- `status` (`QUEUED|RUNNING|DONE|FAILED|CANCELLED`)
- `progress` (0..100)
- `createdAt` (timestamp/uint64)
- `startedAt` (timestamp/uint64, опционально)
- `finishedAt` (timestamp/uint64, опционально)
- `rewardCoinsTotal` (целое)

2.3.2. Каждый заказ всегда производит ровно 1 единицу выбранной продукции.
2.3.3. `rewardCoinsTotal = rewardCoins(item)`.  
2.3.4. Производственное время заказа: `baseTimeMs(item)`.

### 2.4. RatingEntry

2.4.1. Сервер поддерживает глобальный рейтинг игроков.

2.4.2. Запись рейтинга содержит поля:

- `playerId` (целое, уникальное)
- `login` (строка)
- `coins` (целое)
- `doneOrders` (целое, количество завершённых заказов со статусом `DONE`)
- `ratingScore` (целое)
- `place` (целое, позиция игрока в рейтинге)

2.4.3. Базовая формула рейтинга:

- `ratingScore = coins + doneOrders * RATING_DONE_ORDER_BONUS`

2.4.4. Значение `RATING_DONE_ORDER_BONUS` задаётся конфигом/константой сервера.

2.4.5. Рейтинг сортируется по:

- `ratingScore` по убыванию
- при равенстве: `coins` по убыванию
- при равенстве: `playerId` по возрастанию

2.4.6. Рейтинг должен пересчитываться при каждом изменении данных, влияющих на `ratingScore`.

## 3. Протокол: запросы/ответы

### 3.1. Формат сообщений

3.1.1. Каждое сообщение содержит поле `type`.  
3.1.2. Любая ошибка возвращается сообщением:

`{"type":"error","code":"...","message":"..."}`

3.1.3. `code` обязателен, `message` — человекочитаемое.

---

## 4. Команды клиента

### 4.1. Register

**Запрос**: `{"type":"register","login":"alex","password":"qwerty123"}`

**Ответ (успех)**: `{"type":"register_ok","playerId":1,"login":"alex","coins":20,"machines":1}`

**Ошибки**
- `INVALID_LOGIN`
- `INVALID_PASSWORD`
- `LOGIN_ALREADY_EXISTS`

---

### 4.2. Login

**Запрос**: `{"type":"login","login":"alex","password":"qwerty123"}`

**Ответ (успех)**: `{"type":"login_ok","playerId":1,"login":"alex","coins":20,"machines":1}`

**Ошибки**
- `INVALID_LOGIN`
- `INVALID_PASSWORD`
- `UNKNOWN_LOGIN`
- `AUTH_FAILED`

---

### 4.3. Create Order

**Запрос**: `{"type":"create_order","playerId":1,"item":"Gear"}`

**Ответ (успех)**: `{"type":"order_created","orderId":42}`

**Ошибки**
- `UNKNOWN_PLAYER`
- `INVALID_ITEM
- `QUEUE_FULL`

---

### 4.4. List Orders

**Запрос**: `{"type":"list_orders","playerId":1}`

**Ответ (успех)**

`{"type":"orders","items":[{"orderId":42,"item":"Gear","status":"RUNNING","progress":30,"rewardCoinsTotal":2}]}`

**Ошибки**: `UNKNOWN_PLAYER`

---

### 4.5. Get Stats

**Запрос**: `{"type":"stats","playerId":1}`

**Ответ (успех)**: `{"type":"stats","coins":23,"machines":2,"queued":5,"running":2,"done":10,"failed":0}`

**Ошибки**: `UNKNOWN_PLAYER`

---

### 4.6. Buy Machine

**Запрос**

`{"type":"buy_machine","playerId":1}`

**Ответ (успех)**: `{"type":"machine_bought","machines":2,"coins":5}`

**Ошибки**
- `UNKNOWN_PLAYER`
- `NOT_ENOUGH_COINS`

---

### 4.7. Cancel Order (опционально, но рекомендую)

**Запрос**: `{"type":"cancel_order","playerId":1,"orderId":42}`

**Ответ (успех)**: `{"type":"order_cancelled","orderId":42}`

**Ошибки**
- `UNKNOWN_PLAYER`
- `UNKNOWN_ORDER`
- `FORBIDDEN`
- `CANNOT_CANCEL` — если статус `DONE/FAILED/CANCELLED`

---

### 4.8. Get Rating

**Запрос**: `{"type":"rating","playerId":1}`

**Ответ (успех)**:

`{"type":"rating","items":[{"place":1,"playerId":2,"login":"max","coins":120,"doneOrders":7,"ratingScore":190},{"place":2,"playerId":1,"login":"alex","coins":95,"doneOrders":6,"ratingScore":155}]}`

**Ошибки**
- `UNKNOWN_PLAYER`

### 4.9. Rating Updated (server push / live update)

Сервер может отправлять это сообщение клиенту без отдельного запроса при изменении рейтинга.

**Сообщение**:

`{"type":"rating_updated","items":[{"place":1,"playerId":2,"login":"max","coins":120,"doneOrders":7,"ratingScore":190},{"place":2,"playerId":1,"login":"alex","coins":95,"doneOrders":6,"ratingScore":155}]}`

## 5. Сервер: обработка производства

### 5.1. Очередь и воркеры

5.1.1. Сервер содержит очередь заказов `ProductionQueue`.  
**5.1.2.** На сервере создаётся **фиксированный пул потоков производства** `WORKER_POOL_SIZE` (задаётся конфигом/константой) и **не изменяется** при апгрейдах.
**5.1.3.** `machines` игрока означает **максимальное число одновременно выполняющихся (`RUNNING`) заказов этого игрока**.
**5.1.4.** Каждый заказ производит ровно 1 деталь.
**5.1.5.** Заказ может оставаться в `QUEUED`, пока у владельца нет свободного слота (`runningCount < machines`).

### 5.2. Статусы

5.2.1. После создания заказ получает `QUEUED`.  
5.2.2. При начале выполнения заказ получает `RUNNING`, фиксируется `startedAt`.  
5.2.3. При успешном окончании:

- статус `DONE`
- `progress = 100`
- начисляются `rewardCoinsTotal` владельцу
- фиксируется `finishedAt`

5.2.4. При отмене:

- если `QUEUED` → статус `CANCELLED`, в работу не берётся
- если `RUNNING` → сервер должен поддерживать кооперативную отмену (периодическая проверка cancel-флага), затем `CANCELLED`

### 5.3. Прогресс

5.3.1. Прогресс обновляется дискретно (например раз в `TICK_MS`), минимум 5 обновлений за время выполнения заказа.  
5.3.2. Прогресс должен быть монотонным (не уменьшаться).

### 5.4. Рейтинг

5.4.1. Сервер хранит актуальный глобальный рейтинг всех игроков.

5.4.2. Рейтинг должен обновляться при:

- создании нового игрока
- успешном завершении заказа (`DONE`)
- изменении количества монет игрока

5.4.3. После пересчёта рейтинга сервер должен отправить всем подключённым клиентам сообщение `rating_updated`.

5.4.4. Обновление рейтинга должно происходить в live-режиме, без необходимости перезапуска клиента.

5.4.5. Сервер обязан гарантировать консистентность рейтинга при конкурентных изменениях состояния игроков.

### 5.5. Аутентификация

5.5.1. Сервер должен поддерживать отдельные операции регистрации и логина.

5.5.2. Логин игрока уникален в рамках всей системы.

5.5.3. Пароль хранится на сервере не в открытом виде, а в виде `passwordHash`.

5.5.4. После успешного логина сервер возвращает существующий `playerId` и текущее состояние игрока, а не создаёт нового игрока.

5.5.5. Все игровые команды используют `playerId`, полученный после успешного логина.

## 6. Клиент (Qt): функциональность UI

6.1. Клиент предоставляет формы регистрации и логина (`login` + `password`).  
6.2. Клиент отображает:
- `coins`, `machines`
- `stats` (queued/running/done/failed)
- таблицу заказов (orderId, item, status, progress, reward)
- таблицу рейтинга (place, player login, coins, doneOrders, ratingScore)

6.3. Клиент позволяет:
- создать заказ (item)
- купить станок
- отменить выбранный заказ

6.4. Клиент получает обновления состояния периодическим запросом:
- каждые `POLL_MS` отправляет `stats` и `list_orders`
- `POLL_MS` задаётся конфигом/константой (например 500–1000 мс)

6.5. Клиент должен получать рейтинг в live-режиме:
- после успешного логина клиент запрашивает `rating`
- при получении `rating_updated` клиент немедленно обновляет таблицу рейтинга без ручного refresh
- обновление рейтинга не должно блокировать UI

## 7. Многопоточность

### 7.1. Сервер

7.1.1. Сервер должен запускать `io_context.run()` минимум в **2 потоках**.  
7.1.2. Производственные воркеры реализуются как **фиксированный thread pool** размера `WORKER_POOL_SIZE`.  
7.1.3. Доступ к общему состоянию (players, orders, queue) должен быть потокобезопасным.
7.1.4. Доступ к структурам рейтинга и рассылке `rating_updated` должен быть потокобезопасным.

### 7.2. Клиент

7.2.1. UI работает в главном потоке.  
7.2.2. Сетевое взаимодействие должно быть вынесено минимум в **1 отдельный поток** (QThread или аналог).  
7.2.3. Обновление UI из фонового потока запрещено; обмен только через сигналы/слоты.

## 8. Unit-тесты (обязательные ФТ к тестам)

### 8.1. Серверные тесты (GoogleTest или Boost.Test)

Должны быть тесты на:
- регистрацию игрока
- логин по корректной паре `login/password`
- ошибки регистрации и логина
- создание заказа (валидные/невалидные данные)
- переходы статусов `QUEUED->RUNNING->DONE`
- начисление монет после `DONE`
- покупка станка (достаточно/недостаточно монет)
- отмена заказа (если реализована)
- конкурентное создание заказов (параллельные вызовы)
- корректный пересчёт рейтинга
- live-рассылку `rating_updated` после изменения рейтинга

### 8.2. Клиентские тесты (Qt Test)

Должны быть тесты на:
- формирование JSON-команд (register/login/create/stats/list/buy)
- парсинг ответов (`register_ok`, `login_ok`, `orders`, `stats`, `rating`, `rating_updated`, `error`)
- генерация сигналов при получении данных (через `QSignalSpy`)
